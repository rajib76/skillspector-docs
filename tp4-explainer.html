rule TP4 · Description-Behavior Mismatch · MEDIUM / HIGH

Does the code do what the description says, or does it do more?

TP4 is the only LLM-powered check in SkillSpector's MCP tool-poisoning analyzer. It sends the skill's declared purpose next to each piece of its code to a model, and turns a confident "mismatch" verdict into a finding. This page walks through the implementation step by step, using the repo's own mcp_mismatched_skill test fixture as the running example.

Source: src/skillspector/nodes/analyzers/mcp_tool_poisoning.py Entry: _check_tp4() · line 1192 Tests: tests/test_mcp_tool_poisoning.py · line 1118+

▸TP4 at a glance, and where duplicates come from

The greeter skill from the walkthrough, traced from files to report. Solid paths always happen for this skill. The dashed path happens only when a script is large enough to be split. Red markers show where extra findings are created (D1, D2) and the two checks that fail to remove them (G1, G2).

How likely duplication is

The number of TP4 findings equals the number of batches the model flags. One batch is created for each chunk of an executable script, plus one for each labeled code block in a Markdown or text file. When the same code appears in two batches, the model will very likely answer the same way for both. So duplication is near-certain whenever the code is copied, and depends on the model's judgment when a big file is split.

0The idea in one picture

Two inputs meet in one prompt: what the skill  claims  (from the SKILL.md frontmatter) and what it  actually contains  (executable files and labeled code fences). Code is split into chunks, and every chunk gets its own LLM call with the full declaration attached.

1The gate: when TP4 runs at all

node() · line ~1932  |  _check_tp4() · lines 1192–1225

TP1–TP3 always run because they are static. TP4 runs after them, and only if three things hold:

  1. state["use_llm"] is truthy. It defaults to True, and the CLI always sets it explicitly.
  2. manifest["description"] is a non-empty, non-whitespace string. With no description there is nothing to compare against, so TP4 returns an empty outcome and makes no LLM call.
  3. The shared runtime budget is not already exhausted. If it is, TP4 records a RUNTIME_LIMIT partial event against SKILL.md and stops.
if state.get("use_llm", True):
    tp4_outcome = _check_tp4(state)
    findings.extend(tp4_outcome.findings)
    ledger.extend(tp4_outcome.ledger)

2Building the declared side

_check_tp4() · lines 1226–1245

Three manifest fields are read and each is cut to TP4_MAX_DECLARATION_CHARS (16,384 characters). Triggers and permissions go through str(), so a YAML list shows up in Python repr form, like ['read']. If any field was cut, a SIZE_LIMIT partial event is recorded once.

Then the model is resolved: model_config["mcp_tool_poisoning"], falling back to model_config["default"] and then the active provider's default. The model's max input window sets the token budget for each chunk:

overhead_tokens    = estimate_tokens(prefix + SUFFIX) + 16
batch_input_tokens = min(TP4_MAX_BATCH_INPUT_TOKENS # 32_000, model_input_tokens)
code_token_budget  = batch_input_tokens - overhead_tokens

If code_token_budget is below 64 tokens (TP4_MIN_CODE_TOKENS), for example because the declaration is huge and the model is small, no code is sent and a SIZE_LIMIT partial event is recorded.

3Collecting the actual side

iter_candidates() · line 1475  |  _iter_tp4_markdown_fences() · line 1002  |  prepare_source() · line 1405

Code comes from state["llm_file_cache"] (falling back to file_cache). A file's language comes from component_metadata[].type, not from its extension. There are two passes:

Pass 1 · executable files

  • Type in _TP4_EXECUTABLE_TYPES: python, javascript, typescript, shell, ruby, go, rust
  • The whole file is one candidate (lines 1…N)

Pass 2 · fences in Markdown/text

  • Only fences with a known label: py, bash, sh, zsh, js, ts, rb, golang, rs…
  • Unlabeled, html, json, empty and unterminated fences are ignored
  • Line numbers are kept relative to the .md file

Before a file is used, prepare_source() applies the aggregate limits: at most 128 files, 1 MB per file and 4 MB in total. Truncation goes through _bounded_utf8_prefix() so a multi-byte character is never split. Whitespace-only files are skipped.

4Line-aligned chunking

      
budget: _check_tp4() · lines 1239–1247  |  split: _tp4_line_chunks() · line 1083  |  batch build: plan_candidate() · lines 1293–1395

      
Splitting happens in two stages. First TP4 works out how many tokens of code fit in one prompt. Then _tp4_line_chunks() cuts each candidate into pieces of that size, keeping whole lines.


      
Stage 1: the code budget for each chunk

      
prefix             = _TP4_PROMPT_PREFIX.format(description=…, triggers=…, permissions=…)
overhead_tokens    = estimate_tokens(prefix + _TP4_PROMPT_SUFFIX) + 16
batch_input_tokens = min(TP4_MAX_BATCH_INPUT_TOKENS, model_input_tokens)   # min(32_000, model limit)
code_token_budget  = batch_input_tokens - overhead_tokens

      
    
        
  • Overhead is the fixed prompt text plus the skill's declaration. A longer description leaves less room for code.
    • 
        
  • The cap is 32,000 tokens, or the model's input limit if that is smaller.
    • 
        
  • Typical result: about 32,000 − ~250 ≈ 31,750 tokens, roughly 127 KB of code at 4 characters per token.
    • 
        
  • Below 64 tokens (TP4_MIN_CODE_TOKENS), no code is sent at all and a SIZE_LIMIT event is recorded.
    • 
      

      
Before chunking, prepare_source() cuts each file to at most 1 MB, and all files together to 4 MB. _bounded_utf8_prefix() cuts on a character boundary, so multi-byte UTF-8 characters are never broken.


      
Stage 2: _tp4_line_chunks(content, max_tokens)

      
for line_number, line in enumerate(content.splitlines(keepends=True), start=1):
    line_tokens = max(1, (len(line) + 3) // 4)          # ≈ ceil(chars / 4)

    if line_tokens > max_tokens:                         # one line bigger than the whole budget
        flush current chunk
        yield _TP4CodeChunk(None, line_number, …)        # placeholder → skipped, SIZE_LIMIT event
        continue

    if current and current_tokens + line_tokens > max_tokens:
        flush current chunk                              # full: start a new one at this line
    current.append(line); current_tokens += line_tokens

6The LLM call and its typed answer

      
_TP4Analyzer · line 932  |  _TP4AnalysisResult · line 914

      
_TP4Analyzer subclasses the shared LLMAnalyzerBase and sets response_schema = _TP4AnalysisResult, so the provider is asked for structured output in this shape:

      
class _TP4AnalysisResult(BaseModel):
    is_mismatch: bool
    confidence: float = 0.0            # validator: must be 0.0–1.0
    declared_purpose_summary: str = ""
    actual_behavior_summary: str = ""
    mismatched_capabilities: list[str] = []
    explanation: str = ""

      
All batches go out together through run_async(analyzer.arun_batches_detailed(batches)). Concurrency is capped by SKILLSPECTOR_MAX_LLM_CONCURRENCY, and results keep batch order. The outcome comes back in four buckets: successful, recovered, warnings and failures.

      
Format recovery. If the model returns malformed output, the base class can rebuild the object field by field. recovery_required_fields = ("confidence",) forces confidence to be recovered even though it has a default. Without that, a recovered result could silently fall to 0.0 and drop under the threshold. This is the "retry malformed TP4 responses" fix listed in the CHANGELOG.

Text fields are bounded too: the declared summary is cut to 512 characters, the actual summary to 1,024, at most 16 capabilities of 256 characters each, and the message and explanation to 4,096.     • 
        
  • Refusals. If every failure is a model refusal (LLM_RESPONSE_REFUSED), the LLM call record is marked not-ok but carries no error string.
    • 
        
  • Deadline hit mid-run. LLMRuntimeLimitError marks all unfinished batches PARTIAL / RUNTIME_LIMIT.
    • 
        
  • Any other exception. It is logged as a warning, unfinished batches are marked FAILED / LLM_BATCH_FAILED, and the static TP1–TP3 results are still returned.
    • 
        
  • Telemetry. llm_call_log and inference_usage are emitted only if TP4 actually attempted a call.

9Things to know

      
    
        
  • Severity can be HIGH. The README rule table lists TP4 as MEDIUM, but the code emits HIGH when confidence is 0.7 or above.
    • 
        
  • Location points at SKILL.md. The finding's file is always the manifest. The offending code is only in evidence.code_path and the line range, so tools that read only file will point at the wrong place.
    • 
        
  • One verdict per chunk. parse_response returns exactly one assessment per batch, so a file in N chunks can produce up to N findings, one per chunk with a distinct ID. Nothing merges them later; see section 10.
    • 
        
  • The criteria lean toward precision. The suffix tells the model not to flag supporting implementation details or permissions that are declared but unused. TP4 targets code that does more than declared, not less.
    • 
        
  • Prompt-injection guard. The prefix tells the model to ignore instructions inside the skill content. Skill text and code are still placed in the prompt verbatim, so this defense depends on the instruction alone.
    • 
        
  • Language comes from metadata. A .py file whose component_metadata type isn't "python" will not be reviewed by TP4.
    • 
      

    


    
    

      
10Duplicate findings: how one problem counts twice

      
verified with a scratch test against the real node() and the report's deduplicate()

      
TP4 makes one LLM call per chunk, and every flagged chunk becomes its own Finding. No later stage merges findings that describe the same undeclared behavior. As a result, one problem ("this greeter sends env secrets to evil.example.com") can show up as several TP4 findings and count several times.

The root cause in one sentence: TP4 asks "does this chunk match the description?" once per chunk and keeps every "no" as a separate finding. But the question it's really answering is about the whole skill, and nothing afterwards groups the answers, because the only duplicate checks look for identical IDs or exact text matches, and TP4 findings have neither.

          3
          

            
The report's deduplication skips findings without a fingerprint

            
report.py:2130 runs deduplicate() before counting. It only groups findings that have a fingerprint(), and that requires match_fingerprint or matched_text. TP4 sets neither:

            
# models.py:214 — Finding.fingerprint()
if not self.match_fingerprint and not self.matched_text:
    return None

# deduplicate.py:203
fingerprint = finding.fingerprint()
if fingerprint is None:
    unique_without_match.append(finding)   # passed through untouched
    continue

            
Adding a fingerprint alone would not fix it. The grouping key also includes the message, explanation and evidence (classification_metadata_key, line 91). Those contain the LLM's wording and the chunk's line range, which differ for every chunk.

            
Both findings reach the report and both are counted.

          

        

      

      
The meta-analyzer that runs after all analyzers doesn't help either. It only adds tags and explanations to findings and never removes one (meta_analyzer.py ~line 488).


      
How likely this is in real scans

      
    
        
  • Script plus a Markdown code block (scenario B) is the most common case. Many skills show their script's code in SKILL.md or a README, and each copy is reviewed separately.
    • 
        
  • Big files (scenario A) need more than about 128 KB of code before they split. A real model also judges each chunk on its merits, so the padding-only chunk might not be flagged. But each chunk is still compared against the full declaration, so a large script with network calls spread through it can produce one finding per chunk.
    • 
        
  • Several scripts with the same undeclared behavior give one finding each. Per file this is defensible, but it is still one mismatch with the description.
    • 
        
  • Severity can differ per copy. One chunk may come back at 0.8 (HIGH) and another at 0.6 (MEDIUM), so the same problem can appear at two severities.
    • 
      

      
The opposite problem: because each chunk is judged alone, behavior split across a chunk boundary can be missed. If secrets are read in chunk 1 and sent in chunk 2, neither chunk may look clearly malicious on its own.


      
Suggested fix

      
TP4 checks one claim about the whole skill: does the description match what the code does? So it should produce at most one finding per skill, or one per file. After the batches return, _check_tp4 would:

      
    
        
  1. Collect every assessment with is_mismatch and confidence ≥ 0.5.
    2. 
        
  2. Emit one finding using the highest confidence, which sets its severity.
    3. 
        
  3. Combine and de-duplicate mismatched_capabilities for the message.
    4. 
        
  4. Record every flagged (code_path, start, end) range in occurrences or evidence, so no location is lost.
    5. 
        
  5. Remove the seen_finding_ids check, or replace it with a real key such as (code_path, start, end).
    6. 
      

      
# sketch, after the batch loop in _check_tp4
flagged = [(b, a) for b, a in assessed if a.is_mismatch and a.confidence >= 0.5]
if flagged:
    best_batch, best = max(flagged, key=lambda p: p[1].confidence)
    caps = list(dict.fromkeys(c for _, a in flagged for c in a.mismatched_capabilities))
    finding = _tp4_finding(best.model_copy(update={"mismatched_capabilities": caps}), best_batch, description)
    finding.occurrences = [
        {"file": b.file_path, "start_line": b.start_line, "end_line": b.end_line} for b, _ in flagged
    ]
    result.findings.append(finding)     # one finding, every location kept

      
A regression test would run scenarios A and B and assert exactly one TP4 finding with two occurrences.

    


    
    

      
11How TP4 findings feed the risk score

      
_compute_risk_score() · nodes/report.py:681  |  called at report.py:2127  |  RISK_THRESHOLD · constants.py:35

      
TP4 has no score of its own. Every TP4 finding adds points to the skill's overall risk score (0–100), together with the findings from every other rule. That score decides the verdict and the CLI exit code.


      
The formula

      
contribution = severity_points × repeat_weight × confidence   (× 1.3 if finding.file is executable)
score        = min(100, max(floor, int(Σ contributions over all rules)))

What this means

      
    
        
  • Duplicates raise the score. The score is computed on the findings before de-duplication (report.py:2127 runs before deduplicate() on line 2130). Even if de-duplication worked for TP4, the score would already include the duplicates. In the greeter example, two copies give 33 instead of 23 (+45%), and three give 38 (+65%). The 3-per-rule cap limits this but doesn't stop it.
    • 
        
  • TP4 alone can never block a skill. Its maximum is 43, below the 51 needed for DO_NOT_INSTALL and below the CLI threshold of 50. A greeter that sends secrets to a remote host is rated CAUTION unless other rules also fire, such as the static data-exfiltration rules.
    • 
        
  • The missing 1.3× makes it weaker. With the real script path, one finding would score 29.9 instead of 23. The greeter's three copies (0.92, 0.85, 0.80) would reach 50, still one point below the CLI threshold. Three findings at confidence 1.0 would reach 56, enough for DO_NOT_INSTALL.
    • 
        
  • Order decides which copy gets full weight. Among equal severities, the first-produced finding gets weight 1.0 even if it has lower confidence (33 vs 32 above).
    • 
        
  • Low-confidence MEDIUM findings barely count. A MEDIUM at 0.5–0.69 adds only 5–7 points.
    • 
      

      
Fix direction: merge TP4 into one finding per skill (section 10) so duplicates stop adding points, and set the finding's file to the offending code's real path so the 1.3× executable weighting applies. Whether one TP4 finding should be able to block a skill on its own, for example with a floor like SC8's, is a policy decision for the maintainers.

    


    
    

      
12Can you skip TP4?

      
suppression.py · report.py:2127  |  mcp_tool_poisoning.node() · line ~1932  |  cli.py scan options

      
Partly. SkillSpector can hide TP4's findings and leave them out of the score, or turn off all LLM checks. It has no option that stops only TP4 from running while keeping the other LLM checks.


      

        

          
Option 1 · Baseline rule (recommended)

          
    
            
  • Drops TP4 findings before the risk score is calculated
    • 
            
  • Other LLM checks keep working
    • 
            
  • Can be scoped by skill path or message
    • 
            
  • TP4 still runs, so its LLM calls still cost money
    • 
          

        

        

          
Option 2 · --no-llm

          
    
            
  • TP4 never runs, so no TP4 LLM cost
    • 
            
  • Sets use_llm=False, which node() checks before calling _check_tp4
    • 
            
  • Also turns off the semantic analyzers and the meta-analyzer, leaving only static analysis
    • 
          

        

      


      
Option 1: suppress TP4 with a baseline file

      
# skillspector-baseline.yaml
version: 2
rules:
  - id: "TP4"
    reason: "TP4 duplicates/false positives handled by manual review"

      
skillspector scan ./my-skill --baseline skillspector-baseline.yaml
skillspector scan ./my-skill --baseline skillspector-baseline.yaml --show-suppressed   # still list them, unscored

      
Narrower rules are possible. Every field a rule sets must match, * is a wildcard, and reason is required in version 2:

      
rules:
  - id: "TP4"
    path: "*friendly-greeter*"        # only for one skill
    reason: "…"
  - id: "TP4"
    message: "*network access*"       # only TP4 findings mentioning this
    reason: "…"

      
To accept specific known findings instead of the whole rule, skillspector baseline <path> generates exact per-finding entries (fingerprints). Later scans then report only new findings.

Option 2: turn off all LLM checks

      
skillspector scan ./my-skill --no-llm

    tp4_outcome = _check_tp4(state)


      
What doesn't exist

      
    
        
  • No flag to turn off one rule or analyzer. The scan options are --exclude, --baseline, --no-llm, --yara-rules-dir and similar. There is nothing like --disable-rule TP4.
    • 
        
  • The TP4 limits can't be set to zero. SKILLSPECTOR_TP4_MAX_BATCHES must be between 1 and 4096, so it can cap TP4 but not switch it off.
    • 
        
  • --exclude skips files, not rules. Excluding a script hides it from every analyzer, and the report marks it as uninspected.
    •
